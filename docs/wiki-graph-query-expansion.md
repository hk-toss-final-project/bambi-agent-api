## 1. 문제

`agent/graph.py`의 `load_context` 노드는 개인 Wiki 검색과 실시간 수집 양쪽에 토픽
문자열 **하나**를 그대로 넘긴다.

```python
hybrid = await prag_003(connection, user_id=..., query=state["topic"])   # 개인 Wiki
collect_live_context(state["topic"], state["user_id"], model=...)        # 외부 수집
```

그 결과 '코스피'로 리포트를 만들면 제목에 '코스피'가 든 자료만 걸린다. 서킷 브레이커
발동이나 투자자 예탁금 급감을 다룬 기사는 코스피에 관심 있는 사용자에게 중요하지만,
키워드가 겹치지 않으면 수집되지 않는다.

**그런데 그 연결 정보는 이미 DB에 있다.** Wiki Builder가 문서를 만들면서 노드 간
관계를 추출해 저장해 두었다(2026-07-27 기준 61건).

```
코스피     --[applies_concept]--> 서킷-브레이커
코스피     --[applies_concept]--> 투자자-예탁금
삼성전자    --[applies_concept]--> 레버리지-상품 · 성과급-충당금 · 수급-불안감
미국       --[entity_relation]--> sk하이닉스
```

## 2. 제안

토픽의 Wiki 노드에서 관계를 따라 이웃 노드를 찾고, 그 제목을 **보조 검색어**로 함께
수집한다.

```
'코스피'
   ├─[applies_concept]→ 서킷-브레이커
   └─[applies_concept]→ 투자자-예탁금

수집 검색어: "코스피" + "서킷 브레이커" + "투자자 예탁금"
```

일반적인 동의어 확장("코스피 = KOSPI = 종합주가지수")과 다르다. 이 관계는 **사용자가
클리핑한 글에서 추출된 것**이므로 그 사람 고유의 관심 구조를 반영한 개인화 확장이다.

### 이미 같은 계열의 작업이 있다

| | 쓰는 데이터 | 무엇을 정하나 | 상태 |
|---|---|---|---|
| 토픽 성격 판정 | `wiki_documents.document_kind` | 얼마나 **오래된** 자료까지 볼지 | ✅ 구현됨 (2026-07-27) |
| **그래프 확장** | `wiki_document_relations` | **무엇을** 볼지 | 이 문서 |

둘 다 "Wiki가 이미 내린 판단을 리포트가 재사용한다"는 같은 원칙이다. 성격 판정은
`agent/assistant/features/topic_intent.py`를 참고한다 — LLM을 새로 부르지 않고
Wiki 분류를 읽어 쓰는 패턴이 그대로 적용된다.

## 3. 착수 전에 해결해야 할 선행 조건

최초 확인한 세 가지 중 degree 전달 배관은 수정됐고(3.1), 허브 문제는 오판으로
판명돼 철회했다(3.3). 남은 것은 고립 노드 비율(3.2) 하나다.

### 3.1 ✅ 해결 — degree가 관심사 계산에 전달되지 않았다

관계 61건이 저장돼 있는데 `user_interests.attributes.degree`는 **전부 0.0**이다.
그 결과 `structure_weight = 1.0 + log1p(0) = 1.0`으로 모든 노드가 동점이 되고,
관심사 20건의 score가 전부 `1.000`으로 나온다(정렬이 알파벳순인 것이 증상).

```
실측(2026-07-27, mock-clipping-user):
  wiki_document_relations   61건 저장됨
  user_interests.degree     20건 전부 0.0
```

원인은 Wiki Build 자동 재계산이 쓰는 커넥션 저장소의
`load_interest_documents_for_user`가 문서만 조회하고 관계·원본 집계를 누락한
것이었다. 수동 재계산 저장소에는 올바른 집계 SQL이 있었지만 두 경로가 갈라져
자동 재계산 결과에만 `degree=0.0`이 저장됐다.

2026-07-28에 관계 유형 가중 degree와 `source_count`·`source_types`·
`last_activity_at` 집계를 커넥션 함수로 옮기고, 수동·자동 경로가 그 함수 하나를
공유하도록 수정했다. 기존 활성 관심 Profile은 저장된 Snapshot이므로 배포 후
재계산해야 새 degree가 반영된다.

### 3.2 (중요) 관계 추출이 같은 글 안에서도 94%를 놓친다

```
노드 130개 · 연결된 노드 71개 · 고립 59개 (45%)
```

고립 노드는 확장할 이웃이 없어 이 기능의 혜택을 받지 못한다. 실제로 이번 실측의
문제 주제였던 `DDD(Domain-Driven Design)`가 **관계 0건**이었다 — 즉 **그래프 확장을
해도 DDD 사례는 개선되지 않는다.**

#### 원인 추적 (2026-07-28) — 문서가 달라서가 아니다

"고립 45%"는 증상이다. 원인을 좁히려고 **같은 원본 글을 공유하는 노드 쌍** 중
관계가 없는 것을 셌다. 같은 글에 함께 등장했다면 최소한 연결 후보이기 때문이다.

```
같은 원본을 공유하는 노드 쌍   1,135개
그중 관계가 저장된 쌍             61개
연결되지 않은 쌍               1,074개  (94%)
```

**같은 문서 안에서도 관계 대부분이 추출되지 않는다.** 공유 원본이 많은 쌍부터
보면 명백하다.

| 쌍 | 함께 등장한 글 | 관계 |
|---|---|---|
| `anthropic` ↔ `openai` | 4편 | 없음 |
| `anthropic` ↔ `github-action` | 4편 | 없음 |
| `openai` ↔ `openrouter` | 4편 | 없음 |
| `코드베이스-위키` ↔ `자동-문서-업데이트` | 3편 | 없음 |

즉 "여러 글에 흩어져 있어 잇지 못했다"는 가설은 성립하지 않는다. 한 문서 안에서
LLM이 핵심 관계 몇 개만 뽑고 나머지를 버리는 것으로 보인다.

같은 실측에서 함께 확인된 두 가지:

1. **중복 노드** — `코스피`(연결됨)와 `코스피지수`(고립)가 별도로 있고, `주가`는
   `entity`와 `concept` 양쪽에 존재한다. 주식 개념(`외국인-순매수`,
   `시가총액-방식`, `변동성`, `영업-이익`)이 모두 고립이라 `코스피`와 이어지지
   않는다.
2. **`root`는 분석 노이즈다** — `schema/schema.md`의 `root` 노드는 전체 노드를
   나열한 목차라 모든 노드와 원본을 공유한다. 관계 분석에서 제외해야 한다.

- 소유: LLM Wiki 팀 (관계 추출 품질)
- 재현: 같은 `source_document_version_id`를 공유하는 문서 쌍을
  `wiki_document_relations`와 대조하면 된다.

### 3.3 ✅ 문제 아님 — 상위 허브는 정당한 관심 주제였다

> 이 절의 앞선 버전은 "최상위 허브가 지식이 아니라 클리핑 도구"라고 적었다.
> **틀렸다.** 노드 이름(`openwiki`, `obsidian-web-clipper`, `geeknews`)이 도구처럼
> 보인다는 이유만으로 클리핑 인프라가 새어 들어온 것으로 넘겨짚었고, 노드 내용도
> 클리핑 원본도 확인하지 않았다.

```
openwiki               21개 연결  ← 1위
sk하이닉스                8개
obsidian-web-clipper    5개
geeknews                3개
```

실제 관계를 열어 보면 모두 **사용자가 읽은 주제에서 나온 정당한 연결**이다.

```
openwiki             --[applies_concept]--> 자동-문서-업데이트 · 코드베이스-위키 · 코딩-에이전트
                     --[entity_relation]--> anthropic · openai · langchain · vercel · neon
obsidian-web-clipper --> llm-wiki · 개인-지식관리 · markdown · 템플릿
geeknews             --> 데이터-품질 · 코딩-에이전트 · 신입-엔지니어의-가치
sk하이닉스             --> 주가 · 수급-불안감 · adr-상장 · 레버리지-상품
```

`openwiki` 노드의 원본은 "OpenWiki: Open Source Repo Documentation for Coding
Agents" 등으로, **사용자가 그 오픈소스 프로젝트에 관한 글을 여러 편 읽은 것**이다.
클리핑 원본 URL도 facebook·slack·compuzone·dart.fss·yanolja·youtube·finance.naver
등으로 흩어져 있어, "OpenWiki 사이트에서 클리핑해 그 이름이 허브가 됐다"는 가설과
맞지 않는다.

`geeknews`가 `데이터-품질`·`코딩-에이전트`와 연결된 것도 사이트 이름이 메타데이터로
새어든 것이 아니라 **거기서 읽은 글의 주제**다. 구조가 `sk하이닉스`와 동일하다.

**따라서 degree 21은 정확한 신호이고, 수집 키워드로 써도 문제가 없다.** 확장 구현
시 별도 제외 규칙이 필요하다는 앞선 결론도 함께 철회한다.

## 4. 설계 결정 항목

선행 조건이 풀린 뒤 정해야 할 것들. 괄호 안은 현재 시점의 잠정 권고다.

| 항목 | 질문 | 잠정 권고 |
|---|---|---|
| 확장 깊이 | 직접 이웃만? 2홉까지? | **1홉** — 2홉은 주제가 흐려지고 비용이 제곱으로 는다 |
| 확장 폭 | 이웃이 10개면 10번 더 검색하나 | **상위 2~3개** — degree나 관계 가중치로 정렬해 상한 |
| 관계 종류 | 어떤 relation_type을 따를까 | `applies_concept` 우선. `entity_relation`은 실측 후 판단 |
| 점수 가중 | 이웃 검색어로 찾은 자료를 원 키워드와 동급으로 볼까 | **감점** — 원 키워드 유사도로 채점하되 수집만 넓힌다 |
| 제외 규칙 | 별도 제외 목록이 필요한가 | **불필요** — 3.3 확인 결과 상위 허브가 정당한 주제였다 |
| 실패 처리 | Wiki 조회 실패 시 | 원 키워드만으로 진행(topic_intent와 같은 폴백 원칙) |

### 비용이 가장 큰 제약이다

수집은 소스 3개(뉴스·YouTube·Reddit)를 각각 호출한다. 검색어를 N개로 늘리면
**수집 시간이 대략 N배**가 된다.

```
현재 실측:  리포트 1건 41.5초 (검색어 1개)
이웃 3개 추가 시 추정:  120초 이상
```

Worker lease가 600초이므로, 확장 폭을 통제하지 않으면
[리뷰 P0 #4](archive/2026-07/langgraph-agents-review-2026-07-26.md)(lease 초과 → Job 이중 실행)가
다시 문제가 된다. **Step 3(Global 풀 소비 전환)과 함께 가야 안전하다** — 풀에서
읽으면 검색어가 늘어도 네트워크 호출이 늘지 않기 때문이다.

> 2026-07-28 확인: 풀 **검색 기능은 이미 있다.** `prag_003`이 개인 Wiki와 Global
> 풀을 함께 훑는다(풀에 48건을 채우고 실행해 확인). 다만 현재 `load_context`는
> 풀에서 결과를 찾고도 **실시간 수집을 그대로 다 수행**하므로, 이 문서의 비용
> 완화 전제(=풀에서 읽으면 네트워크 호출이 안 는다)는 Step 3에서 **수집 건너뛰기**가
> 붙어야 성립한다. 상세는
> [assistant-split-proposal.md의 Step 3 범위 정정](archive/2026-07/assistant-split-proposal.md) 참고.

## 5. 검증 계획

구현 시 다음을 실측해 기록한다(AGENTS.md 규칙 8).

1. **개선 케이스**: 이웃이 있는 토픽(`코스피`, `삼성전자`)에서 수집·선정 건수가
   확장 전후로 얼마나 늘었나
2. **무영향 케이스**: 고립 토픽(`DDD`)에서 결과가 그대로인가 (회귀 없음 확인)
3. **소요 시간**: 확장 폭별 리포트 생성 시간 — lease 한도 대비 여유
4. **오염 여부**: 이웃 검색어로 들어온 자료가 원 주제와 무관하지 않은가
   (유사도 필터 통과율로 측정)

확장이 켜지고 꺼지는 것을 환경변수로 제어해, 같은 데이터에서 A/B 비교가 가능하게
한다.

## 5.1 실측 결과 (2026-08-06)

로컬 `agent-db`(문서 494 · 관계 599 · 사용자 4명)와 실제 뉴스 검색으로 측정했다.
LLM은 호출하지 않았으므로 요약·유사도 필터 이후 구간은 포함되지 않는다.

### 검색어 전/후

| 토픽 | Wiki 이웃 | 확장 전 | 확장 후 |
|---|---|---|---|
| 코스피 (`user/mock-clipping-user`) | 코스닥시장 | `코스피` | `코스피` + 코스닥시장 |
| DDD 아키텍처 (`user/28`) | Application Layer | `DDD 아키텍처` | `DDD 아키텍처` + Application Layer |

- **개선 케이스**(§5-1): 코스피 수집 15건 → 30건(신규 15건, 중복 0).
- **무영향 케이스**(§5-2): §3.2에서 관계 0건이던 DDD가 현재 1건이다. 회귀 없음.
- **소요 시간**(§5-3): 10.8초 → 23.0초. 이웃 조회 자체는 1.1~6.8ms로, 비용은
  전적으로 늘어난 검색어 수에서 나온다.
- **오염 여부**(§5-4): 제목 기준 증시 관련 비율 97%(29/30). 유사도 필터 통과율은
  LLM 호출이 필요해 미측정.

### organization subtype을 제외한 근거

제외 규칙은 §3.3에서 "불필요"로 정리했지만, **기관·언론사 노드는 예외**임을
실측으로 확인했다. 필터 없이 돌리면 코스피의 이웃 6개 중 5개가 organization이었다.

| 이웃 | subtype | 증시 관련 제목 |
|---|---|---|
| 코스닥시장 | other | 14/15 |
| 코스콤 · 인포스탁 | organization | 6/15 |
| 에프앤가이드 · 한국예탁결제원 | organization | 3/15 |
| KG제로인 | organization | 0/15 |

코스콤으로 검색하면 "임직원 멘탈케어 박람회 개최" 같은 회사 홍보 기사가, 인포스탁
(언론사)으로 검색하면 그 매체의 전체 기사가 걸린다. 기관명은 **주제**가 아니라
**주체**라서 뉴스 검색어로 성립하지 않는다.

| | 수집 | 주제 적합 | 소요 |
|---|---|---|---|
| organization 포함 | 45건 | 60% | 30.6초 |
| **organization 제외** | 30건 | **97%** | 23.0초 |

이 필터는 §3.3이 철회한 "도구 노드 이름 제외 목록"과 다르다. 이름을 보고 넘겨짚는
것이 아니라 Wiki가 이미 부여한 subtype을 쓰고, 위 실측이 근거다.

### 남은 문제 — 이웃 가중치가 동점이다

필터 전 코스피 이웃 6건은 가중치가 **전부 1.0**이었다. 상위 N개를 고르는 실질
기준이 제목 정렬 순이 된다. 현재는 필터로 후보가 1개만 남아 드러나지 않지만,
이웃이 많은 토픽에서는 2차 정렬 기준(이웃 자신의 degree, 원문 공동 출현 수)이
필요하다.

## 6. 요약

- 제안 자체는 타당하다. Wiki가 만든 관계를 리포트가 안 쓰고 있는 것은 사실이다.
- 관심사 degree 전달 배관은 수정됐다. 기존 Profile 재계산 후 연결 수가 점수에
  반영되는지 운영 데이터로 확인해야 한다.
- 상위 허브가 클리핑 도구라고 본 것은 오판이었다(3.3). 노드 이름만 보고 판단한
  결과이며, 실제 관계는 모두 정당한 관심 주제였다. 제외 규칙도 불필요하다.
- 남은 제약은 **관계 추출 누락**(3.2) 하나다. 노드의 45%가 고립인데, 원인은
  문서가 흩어져서가 아니라 **같은 글 안에서도 관계 쌍의 94%가 추출되지 않기**
  때문이다(1,135쌍 중 1,074쌍 미연결). 이웃이 없는 토픽은 확장 혜택을 받지
  못한다(예: DDD).
- 따라서 남은 순서는 **3.2 관계 추출 개선 → 이 문서의 구현**이다.
- 비용 때문에 Step 3(풀 소비 전환)과 묶는 것이 안전하다.

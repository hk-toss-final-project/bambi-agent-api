# Global 수집 스케줄링 협의안 (Step 4)

> 상태: **협의 대기** · 작성일 2026-07-28
> 대상: Service 팀 (우석님 경유) · 관련 [assistant-split-proposal.md](assistant-split-proposal.md) Step 4
> 배경: 리포트 생성이 Global 풀을 우선 소비하도록 전환했으나(Step 3 완료),
> 풀을 채우는 주체가 없어 **수동 CLI로만 채워진다.**

## 1. 무엇을 요청하는가

**관심사 키워드로 수집 Job을 주기 발행해 주십시오.**

현재 Agent 쪽에서 손으로 실행하는 것이 이것이다.

```bash
uv run python -m workers.main --worker global-collector --keywords "코스피"
uv run python -m workers.main --worker global-collector --keywords "삼성전자"
# 주제마다 반복 (2026-07-28: 12회 수동 실행)
```

아키텍처 원칙상 **스케줄·정책은 Service Layer 소유**이므로
([service-integration-guide.md](service-integration-guide.md) §1), Agent가 스스로
주기 실행을 정할 수 없다.

## 2. 왜 필요한가 — 지금은 고리가 끊겨 있다

```
사용자 클리핑 → LLM Wiki 개념 추출 → 관심사 목록      ← 여기까지 작동
                                        ✂ 끊김
                     Global 풀 수집 → 리포트 생성      ← 수동
```

관심사(INT-001/011)는 자동 생성되는데, 그 키워드로 수집하는 주체가 없다.

**Step 3의 성과가 하루짜리인 이유**도 이것이다. 수동으로 채운 날은 리포트가
12.7초에 신선한 근거로 나오지만, 다음 날부터 풀이 늙어 다시 실시간 수집(30~40초)
경로로 돌아간다.

## 3. Agent 쪽 준비 상태

| 항목 | 상태 |
|---|---|
| 수집 워커 (`global-collector`) | ✅ 동작. CLI 배치 형태 |
| 본문 수집 워커 (`global-content`) | ✅ 동작. Jina Reader |
| 풀 검색 (`prag_003`) | ✅ 개인 Wiki와 함께 검색 |
| 리포트의 풀 우선 소비 | ✅ 2026-07-28 완료 |
| **주기 발행** | ❌ **없음 — 이 문서의 요청 사항** |

수집 품질 관련 선결 조건은 오늘 두 건을 해결했다.

- 영문 고유명사 커버리지 — `google_news` Provider 추가 + URL 디코딩
  (Naver 단독으로는 'Cloudflare' 수집 10건 중 관련 3건이었다)
- 근거 본문 품질 — Jina 원문에서 사이트 메뉴를 걷어내고 기사 시작점부터 사용

## 4. 결정이 필요한 항목

### 4.1 발행 주기

수집은 외부 API를 호출하므로 주기가 곧 비용·한도다.

| 후보 | 장점 | 우려 |
|---|---|---|
| 1시간 | 뉴스형 토픽이 항상 신선 | Naver 일 25,000회 한도 대비 여유는 있으나 사용자 증가 시 재검토 |
| 6시간 | 균형 | 장중 급변(예: 코스피 서킷브레이커)을 놓칠 수 있음 |
| 24시간 | 비용 최소 | 뉴스형 토픽은 사실상 항상 콜드 |

**Agent 쪽 의견**: 토픽 성격에 따라 다르게 가는 것이 맞다. Agent는 이미
개념형/뉴스형을 판정하고 있으므로(`topic_intent`, Wiki `document_kind` 기반),
Service가 그 구분을 받아 주기를 달리할 수 있다.

### 4.2 대상 키워드 선정

관심사 20개를 전부 돌릴지, 상위 N개만 돌릴지.

2026-07-28에 degree 전달 버그가 수정되어 **관심사 점수가 이제 변별력을 갖는다.**

```
OpenWiki 1.000 · SK하이닉스 0.782 · Obsidian Web Clipper 0.682 · 레버리지 상품 0.638 …
```

다만 관심사에 도구·계정명이 섞인다(`choi.openai`, `Blob`). 수집해도 뉴스가 없어
0건으로 끝난다(실측: 20개 중 4개가 0건).

**결정 필요**: Service가 발행 전에 거를지, Agent가 수집 실패를 그냥 허용할지.
`AutoWiki`처럼 **실제로 뉴스가 없는** 정상 키워드도 있어 0건을 곧바로 오류로 보면
안 된다.

### 4.3 Job 형태

`global-collector`를 CLI 배치에서 `job_type` 워커로 승격해야 한다. 기존
`report_generation` Job과 같은 발행·Claim 구조를 쓰면 되는지, 별도 취급이 필요한지.

**주의**: `--keywords`는 쉼표 목록을 **하나의 검색어로 이어붙인다**
(`global_source_collector.py:109`). 주제 여러 개를 모으려면 **주제마다 Job을 따로
발행**해야 한다. 한 Job에 여러 키워드를 담으면 "코스피 삼성전자 코스피" 같은 단일
질의가 되어 0건이 나온다(실측).

### 4.4 사용자별 vs 전역

Global 풀은 소유자가 없는 공유 캐시다. 사용자 A의 관심사로 수집한 문서를 사용자 B도
쓴다.

**결정 필요**: 같은 키워드를 여러 사용자가 관심사로 가질 때 중복 발행할지, Service가
합집합을 만들어 한 번만 발행할지. 중복 발행해도 `canonical_url` 충돌로 저장은
중복되지 않지만 외부 API 호출은 낭비된다.

## 5. 참고 — 오늘 실측

풀이 채워졌을 때와 아닐 때의 차이.

```
코스피 리포트
  풀 있음   12.7초 · 근거에 당일 급락·서킷브레이커 발동 사실 포함
  풀 없음   30~40초 · 실시간 수집 경로

리센느 리포트
  풀 있음   11.2초 · 근거에 음악방송 1위·브랜드 모델 발탁 등 구체적 사실
```

Agent 쪽 판정은 양방향으로 작동한다. `Anthropic`은 풀 자료가 잡음 수준이어서
필터가 걸러내고 실시간 수집으로 갔다 — **풀이 있다고 무조건 쓰지 않는다.**

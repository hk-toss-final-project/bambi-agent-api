# 다중 주제(topics) 리포트 생성 벤치마크 — 2026-08-07, gpt-4.1-mini

## 실행 배경

사용자가 관심사 키워드를 여러 개 고르면 한 리포트가 주제마다 별도 섹션을 써야
한다는 요구사항 확인 중, `topics` 인자를 쓰는 다중 주제 경로가 벤치마크 대상이
아니었음을 발견했다(`bench/report_generation`은 `topic` 단일 케이스만 다룸).
이 벤치마크를 신설해 다중 주제 경로만 따로 측정한다.

- 프롬프트 버전: `agent/prompts/templates/report_builder_system.md` (변경 없음) +
  `agent/report_builder/features/generation.py`의 `generate_report_content`
  user prompt(이번 실행 중 2건 수정, 아래 참고)
- 코드 상태: 커밋 `9cc05f1` 기준 워킹 트리, `generation.py` 미커밋 상태로 수정
- 모델: gpt-4.1-mini (공유 클라이언트 기본값)
- 데이터셋: `dataset.jsonl` 12케이스 (신설)

## ⚠️ 이 벤치마크가 측정하지 못하는 것

`run.py`는 `generate_report_content`를 **직접** 호출하고 근거 문서를 데이터셋에서
그대로 주입한다. 실제 수집·풀 검색·`agent/selection` 선별·Critic 재작성 루프는
지나지 않는다. 측정 대상은 "받은 근거를 주제별로 정확히 나눠 쓰는가"로 한정된다.

## 발견 및 조치 (같은 세션에서 코드 변경 후 재실행)

### ① 근거 상한 절단 시 뒤쪽 주제가 통째로 유실 (수정함)

`generate_report_content`가 근거 블록을 16,000자 상한까지 쌓다가 넘으면
`break`로 전체 루프를 멈췄다. 주제 목록 순서상 앞쪽 주제의 근거가 크면, 상한
이후의 모든 주제(자기보다 작은 근거를 가진 주제 포함)가 통째로 사라진다.
실제 운영에서 풀 문서는 최대 62,000자까지 나온 사례가 있어([pool_context.py:202](../../../agent/report_builder/features/pool_context.py)),
가상 시나리오가 아니라 실사용에서 재현 가능한 결함이다.

`break` → `continue`로 수정(`generation.py:141-145`). 이 근거 하나만 건너뛰고
뒤에 더 작은 근거가 있으면 계속 시도한다.

- 검증: `long-context-truncation` 케이스(중간에 낀 거대 근거 1건 + 그 뒤 작은
  주제 2건 배치) — 수정 후 거대 근거를 낸 주제만 유실되고, 그 뒤 주제는
  살아남음을 확인.
- 이 수정은 "근거 상한 자체"는 해소하지 않는다. 문서 단위로 잘라 넣는 대신
  요약해서 예산을 아끼는 방안은 별도 논의 필요(사용자 제안, 미착수).

### ② 소주제명이 길면 Markdown 제목(`###`)을 아예 안 씀 (수정함)

1차 실행(수정 전)에서 `long-topic-names` 케이스가 유일하게 실패했다. 인용은
3개 주제 모두 정확했지만, LLM이 `###` 없이 문단으로만 구분해 채점기가 "제목
없는 섹션 하나에 세 주제 인용이 섞였다"고 판정했다. 원인은 user prompt가
"각각 별도 섹션으로"라고만 지시하고 **형식을 명시하지 않았기** 때문.

`generation.py`의 다중 주제 지시문에 `'### 소주제명' 형식의 Markdown 제목을
반드시 붙일 것`을 명시하도록 수정. 재실행 후 `long-topic-names`도 통과.

## 남은 한계 / 후속 논의

- **근거 상한(16,000자) 자체는 그대로.** `continue` 수정은 "억울한 유실"만
  막을 뿐, 근거 총량이 예산을 넘는 근본 원인은 해소하지 않는다. 문서 단위
  하드 절단(`critic.py`의 `_SOURCE_MAX_CHARS` 패턴) 또는 LLM 요약 캐싱 중
  선택이 필요(사용자 제안, 미착수 — 별도 승인 후 진행).
- 이 벤치마크는 생성 프롬프트 단계만 측정한다. 실제 수집·풀 검색·선별을 통과한
  근거로 다중 주제 리포트를 만들 때도 같은 결과가 나오는지는 별도 파이프라인
  벤치마크가 필요하다(기존 `report_generation` 벤치마크의 07-28 기록에 남은
  같은 한계).

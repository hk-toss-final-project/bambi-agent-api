**주제어만으로는 안 나오는 문서를 13건 중 13건 모두 찾아냈다.**

```
exp-01 코스피    → ['코스피', '서킷 브레이커', '투자자 예탁금', ...]
```

무관한 문서를 끌어온 케이스도 **0건**이다. `edge-02-ambiguous`는 코퍼스에

## 나쁜 것 — 멈출 줄 모른다

### 문제 1. 반복 상한을 87%가 들이받는다

15케이스 중 **13건이 `max_iterations`(5회)까지 갔다.** 스스로 "충분하다"고
판단해 끝낸 것은 2건뿐이다.

프롬프트에는 이렇게 적혀 있는데 지켜지지 않았다:

```
4. 근거가 3건 이상 모이면 그만 찾고 요약한다.
```

`noexp-03-kimchi`는 첫 검색 한 번으로 3건을 다 얻고도 계속했다:

```
질의 = ['김치', '김치 발효', '김치 역사', '김치 종류']   → 수집 3건 (첫 질의로 이미 3건)
```

**상한에 걸리면 `notes`(조사 요약)가 비어서 나온다.** 루프가 최종 응답 없이
잘리기 때문이다. 지금 `notes`는 어디서도 쓰이지 않아 눈에 띄지 않았다.

실시간 수집으로 갔다. 즉 판단이 한쪽으로 치우쳐 있다 — 의심스러우면 부른다.

### 왜 문제인가

벤치마크에서는 가짜 수집이라 공짜지만, **운영에서 `collect_live`는 가장 비싼
도구다.** 뉴스·YouTube·Reddit을 실제로 호출하고 그 안에서 LLM 요약까지 돈다.
리포트마다 불필요하게 한 번씩 더 부르면:

- 외부 API 한도를 그만큼 빨리 소진한다 (2026-07-28 실측: GDELT 429)
- 리포트 생성 시간이 늘어 Worker lease(600초)에 가까워진다

## 이 벤치마크가 측정하지 않는 것

- **검색 품질 자체**: 고정 코퍼스에 키워드 규칙으로 맞춘다. 실제 검색(trigram·
  벡터)의 정확도는 대상이 아니다.
- **수집 결과 품질**: `collect_live`가 실제로 쓸 만한 기사를 가져오는지는 별개다.
- **운영 재현성 한계**: 코퍼스가 작아 "3건"에 금방 닿는다. 실제 실행(2026-07-31
  데모)에서는 도구 호출 4회에 `final`로 끝났으므로, 상한 도달률 87%가 운영에서
  그대로 나오지는 않을 수 있다. **다만 실시간 수집 과호출은 코퍼스 크기와
  무관한 판단 문제로 보인다.**

- 반복 상한 도달 86.7% — "3건 모이면 멈춰라"가 지켜지지 않음
- 실시간 수집 판단 53.3% — 창고에서 충분히 얻고도 `collect_live` 호출

## 무엇을 고쳤나

정지 조건을 **수치로 못 박고**, `collect_live` 금지를 그 안에 명시했다.

```diff
- 2. 풀에 쓸 만한 자료가 없거나 부족하면 collect_live로 인터넷에서 수집한다.
-    느리고 비용이 드니 꼭 필요할 때만 쓴다.
- 4. 근거가 3건 이상 모이면 그만 찾고 요약한다.

+ 3. **모은 근거가 3건 이상이면 거기서 멈추고 요약한다.**
+    더 검색하지 말고 collect_live도 부르지 마라. 이미 충분하다.
+ 4. collect_live는 **근거가 3건에 못 미칠 때만** 쓴다.
+    인터넷을 직접 뒤지므로 느리고 비용이 크다. 충분한데 부르면 낭비다.
+ 5. 검색어를 바꿨는데 새로 나온 자료가 없으면 그 방향은 접는다.
+    비슷한 말로 바꿔 가며 같은 검색을 반복하지 마라.
```

## 대가 — `edge-02-ambiguous` 확장 실패 (재현됨)

주제 `보안`에서 `랜섬웨어` 문서에 닿지 못했다.

```
기준선 질의: ['보안', '랜섬웨어', '보안 취약점']          → d2 찾음
수정 후 질의: ['보안', '정보보안', '사이버 보안',
              '네트워크 보안', '보안 위협']              → d2 못 찾음
```

넓은 주제어에서 구체 용어로 좁히지 못하고 **동의어만 맴돌았다.** 새 원칙 5
("비슷한 말로 반복하지 마라")가 이 케이스에서는 먹히지 않았다.

원인은 확실치 않다. 정지 압력이 커지면서 첫 결과를 깊게 읽기보다 빨리
끝내려는 쪽으로 기운 것으로 보이나, 이 케이스 하나로는 단정할 수 없다.

## 판단

**채택한다.** 잃은 것보다 얻은 것이 크다.

- 잃은 것: 모호한 주제 1케이스의 확장 (13건 중 1건)
- 얻은 것: 불필요한 실시간 수집 사실상 제거, 도구 호출 28% 감소

`collect_live` 과호출은 **운영에서 외부 API 한도를 갉아먹는 실제 비용**이다
(2026-07-28 GDELT 429 실측). 반면 확장 손실은 모호한 주제 한 종류다.

## 남은 숙제

### 1. 데이터셋 기대값이 코드 기준과 어긋난다 (사용자 승인 필요)

`expect_live`를 정할 때 근거 수 기준을 명시하지 않았다. 코드의 기준은
`POOL_MIN_DOCUMENTS = 3`(`is_pool_sufficient`)인데, 데이터셋에는 근거 2건짜리
케이스를 `expect_live: false`로 적어 뒀다.

| 케이스 | 창고 근거 | 데이터셋 기대 | 코드 기준으로는 |
|---|---|---|---|
| exp-04-inflation | 2건 | false | **true여야 함** |
| noexp-02-olympic | 2건 | false | **true여야 함** |
| edge-01-english | 2건 | false | **true여야 함** |
| edge-02-ambiguous | 2건 | false | **true여야 함** |

즉 지금의 "실시간 수집 판단 100%"는 **기대값이 틀린 상태에서 나온 수치**라
그대로 믿으면 안 된다. 4건의 기대값을 `true`로 고치는 것이 맞아 보이나,
데이터셋 변경은 사용자 승인이 필요하다(AGENTS.md 규칙 8). **미승인 상태다.**

### 2. 반복 상한 도달 46.7%는 여전히 높다

절반 가까이가 5회를 다 쓴다. 상한에 걸리면 `notes`(조사 요약)가 빈 채로
반환되는 문제도 그대로다.

### 3. 모호한 주제의 확장 실패

`edge-02` 같은 넓은 주제어에서 구체 용어로 좁히는 능력이 약해졌다. 별도로
케이스를 늘려 경향인지 단발인지 확인이 필요하다.

## 데이터셋 정정 내용

`expect_live` 판정 기준을 정하지 않고 작성해, 창고 근거가 2건인 케이스 4건을
`false`로 잘못 적었다. 코드 기준은 `POOL_MIN_DOCUMENTS = 3`(`is_pool_sufficient`)
이므로 2건은 "부족"이고 실시간 수집이 **맞다.**

| 케이스 | 창고 근거 | 수정 전 | 수정 후 |
|---|---|---|---|
| exp-04-inflation | 2건 | false | **true** |
| noexp-02-olympic | 2건 | false | **true** |
| edge-01-english | 2건 | false | **true** |
| edge-02-ambiguous | 2건 | false | **true** |

기준을 `run.py` 모듈 docstring에 명시해 다시 흔들리지 않게 했다.

## 무엇을 고쳤나

```diff
- 2. 풀에 쓸 만한 자료가 없거나 부족하면 collect_live로 인터넷에서 수집한다.
- 4. 근거가 3건 이상 모이면 그만 찾고 요약한다.

+ 3. **모은 근거가 3건 이상이면 거기서 멈추고 요약한다.**
+    더 검색하지 말고 collect_live도 부르지 마라. 이미 충분하다.
+ 4. collect_live는 **근거가 3건에 못 미칠 때만** 쓴다.
+ 5. 검색어를 바꿨는데 새로 나온 자료가 없으면 그 방향은 접는다.
```

### 수집 판단은 왜 그대로인가 — 오류의 방향만 바뀌었다

```
기준선 : 틀린 3건이 전부 "안 불러도 되는데 불렀다" (과호출)
         exp-03-ev · noexp-03-kimchi · noexp-04-coffee  (모두 근거 3건 보유)

수정 후 : 틀린 3건이 전부 "불러야 하는데 안 불렀다" (과소호출)
         exp-04-inflation · noexp-02-olympic · edge-01-english  (모두 근거 2건)
```

**정확도는 80%로 같고, 추가 오류는 없다.** "3건이면 멈춰라"를 강하게 넣으니
3건 이상에서 멈추는 것은 잘하게 됐지만(과호출 해소), 2건일 때 부족하다고
판단하는 쪽이 약해졌다. 저울이 반대로 기울었을 뿐이다.

### 그럼에도 채택하는 이유

**비용 감소는 데이터셋 기대값과 무관하게 실측된 값이다.**

- 도구 호출 5.13 → 3.73회 (리포트당 LLM 왕복 1.4회 감소)
- 상한 도달 13건 → 7건

그리고 **두 오류 방향의 비용이 다르다.**

| 오류 | 결과 |
|---|---|
| 과호출 (기준선) | 외부 API 한도 소진, 생성 시간 증가 (2026-07-28 GDELT 429 실측) |
| 과소호출 (수정 후) | 근거 2건으로 리포트 작성 — 얕아지지만 실패는 아님 |

과소호출이 덜 위험하다고 판단했다.

## 앞선 보고 정정 2 — `edge-02` 확장 실패는 재현되지 않는다

중간 보고에서 "`edge-02-ambiguous` 확장 실패가 2회 재현됐다"고 적었으나,
3회차에서는 `랜섬웨어`를 검색해 정상적으로 찾아냈다.

```
1·2회차: ['보안', '정보보안', '사이버 보안', '네트워크 보안']      → 못 찾음
3회차  : ['보안', '랜섬웨어', '보안 취약점', '정보보안']            → 찾음
```

**3회 중 2회 실패 — 경계선 케이스지 확정된 회귀가 아니다.** 검토자 벤치마크에서
얻은 교훈(개별 케이스는 흔들린다)을 여기서도 확인했다. 2회로 "재현"을 단정한
것은 성급했다.

## 남은 숙제

1. **수집 판단 80%를 올리려면** 2건일 때의 판단을 손봐야 한다. 다만 지금
   프롬프트를 또 건드리면 반대 방향이 다시 나빠질 수 있다. 프롬프트 대신
   **코드로 강제**하는 편이 나을 수 있다 — `is_pool_sufficient`가 이미 있으므로,
   조사원이 끝난 뒤 근거가 3건 미만이면 `collect_live`를 코드가 부르는 방식이다.
   LLM에게 맡길 판단인지 코드로 정할 규칙인지 재검토가 필요하다.
2. **반복 상한 도달 46.7%**는 여전히 높다. 상한에 걸리면 `notes`가 빈 채로
   반환되는 문제도 그대로다.
3. **케이스가 15건뿐이라** 한 건이 6.7%p를 움직인다. 판단 지표를 더 신뢰하려면
   케이스를 늘려야 한다.
